# UI-автотесты mebel169.ru

Playwright + TypeScript + Allure. Проверки построены на тест-кейсах из документа «Тестирование» (ТК-А-*, ТК-КП-*).

## Быстрый старт

```bash
npm ci
npm run browsers:install          # firefox и chromium для Playwright
cp .env.example .env              # заполнить TEST_USER_* (см. ниже)
npm test                          # все проверки
npm run report                    # собрать и открыть Allure-отчёт
npm run test:report               # прогон + отчёт (отчёт откроется, даже если есть упавшие тесты)
```

Отдельно: `npm run test:auth`, `npm run test:e2e`. Проверка типов: `npm run typecheck`.

**Запуск с видимым браузером:**

```bash
npm run test:headed                                    # все тесты, видимый браузер, по одному
npm run test:headed -- autotest/specs/e2e              # только сквозной сценарий
SLOW_MO_MS=500 npm run test:headed                     # с замедлением действий, чтобы было видно шаги
LOG_LEVEL=debug npm run test:headed -- autotest/specs/auth   # подробный лог
```

Описание страниц и локаторов элементов находится в [docs/PAGES.md](docs/PAGES.md).

## Структура

```

  logger.ts                 winston: DEBUG/INFO/WARN/ERROR, консоль + logs/autotest.log
  secrets.ts                маскирование паролей, контактов, токенов, cookies
  reporting.ts              step() с логированием, метаданные кейса и параметры для Allure
  fixtures.ts               базовые фикстуры: лог теста, скриншот при падении (поля закрашены)
  SanitizingReporter.ts     после прогона маскирует секреты в allure-results / test-results
  data.ts                   загрузка JSON-данных, подстановка {{account.*}} из окружения
  dto.ts, utils.ts          DTO и разбор цен/количеств
ui/                         Page Object: локаторы и детали взаимодействия (описание: docs/PAGES.md)
  elements/                 BaseElement, Input, Choice (радио/чекбокс со стилизованной меткой)
  components/               Header, ProductTile, AddedToCartModal, CartItem, OrderSummaryBlock, ConfirmDialog
  pages/                    LoginPage, AccountPage, HomePage, SearchResultsPage, ProductPage,
                            CartPage, CheckoutPage, OrderSuccessPage
  App.ts                    доступ к страницам + переключение вкладок
autotest/                   сценарии, параметризация, проверки
  fixtures.ts               фикстуры app / auth / shop
  steps/                    общие шаги (вход, очистка корзины)
  data/                     наборы данных (JSON) и их типы
  specs/auth/               10 проверок авторизации
  specs/e2e/                сквозной сценарий
```

Зависимости направлены в одну сторону: `autotest → ui → core`.

## Авторизация: применимые способы и набор проверок

На сайте одно поле «Email или телефон» и пароль. Поэтому применимы оба способа (email + пароль, телефон + пароль), и оба покрыты.

| № | Класс | Набор | ТК |
|---|---|---|---|
| 1 | Позитивная | телефон + пароль | ТК-А-01 |
| 2 | Позитивная | email + пароль | ТК-А-01 |
| 3 | Пустой идентификатор | — | ТК-А-04 |
| 4 | Пустой пароль | — | ТК-А-04 |
| 5 | Неверный формат | телефон «123» | ТК-А-17* |
| 6 | Неверный формат | email «user@@example.com» | ТК-А-17* |
| 7 | Несуществующий аккаунт | телефон | ТК-А-03 |
| 8 | Несуществующий аккаунт | email | ТК-А-03 |
| 9 | Неверный пароль | телефон | ТК-А-02 |
| 10 | Неверный пароль | email | ТК-А-02 |

\* ТК-А-17 нет в исходном документе: класс «неверный формат» требует ТЗ, его нужно добавить в тест-кейсы.

**Известный дефект сайта: вход по email.** Email, указанный при регистрации, не привязывается к аккаунту, поэтому войти по email + паролю невозможно.
- **Набор 2** оставлен в прогоне и **ожидаемо падает** с сообщением «Вход отклонён: „Неверный логин или пароль“». Это найденный автотестом дефект, а не ошибка теста. В Allure набор помечен тегом `known-defect`, описание дефекта есть в карточке теста.
- **Набор 10** формально проходит, но пока дефект не исправлен, он фактически проверяет несуществующий аккаунт, а не неверный пароль. Он тоже помечен `known-defect`.

После исправления дефекта поле `knownIssue` нужно убрать из `autotest/data/auth.json`.

**Позитивные проверки:** переход обратно в магазин, имя пользователя в шапке (`TEST_USER_NAME`) и доступ к защищённой странице ЛК без перенаправления на вход.

**Негативные проверки:** ожидаемое сообщение под нужным полем, поле помечено как ошибочное, пользователь остаётся на форме, а ЛК перенаправляет на вход (сессии нет).

**Особенности сайта:**
- На клиенте проверяются только пустые поля и длина логина меньше 5 символов («Введите не менее 5 символов.»).
- Любой другой неверный формат (например, `user@@example.com`) уходит на сервер и получает общее «Неверный логин или пароль». Это ожидаемый результат в наборе 6.
- Сообщение об ошибке не раскрывает, какое поле неверно. Это соответствует ТК-А-06.

## Сквозной сценарий (E2E-01)

1. **Вход** по телефону (ТК-А-01). По email войти нельзя из-за дефекта сайта, см. выше.
2. **Подготовка:** корзина очищается. У авторизованного пользователя она хранится на сервере.
3. **Поиск** «Диван прямой тулон аликанте серый»: выдача не пуста, первые 5 результатов содержат «диван», в выдаче есть нужный товар.
4. **Карточка** (ТК-КП-01-06): тот же URL, название, вариант «Серый», цена совпадает с ценой в выдаче, кнопка «В корзину» доступна.
5. **Корзина** (ТК-КП-02-01…03): нужный товар и вариант, количество 2, стоимость строки = цена × 2, «Итого» = сумма − скидка.
6. **Оформление** (ТК-КП-02-10, 03-09, 03-13): товар и суммы перенесены, физлицо, контакты, самовывоз, наличные, текст согласия на обработку ПД, кнопка «Подтвердить заказ» активна.
7. **Заказ:** выполняется только при `ORDER_SUBMIT=true`.

## Ограничения и исключения

- **CAPTCHA.** Headless Chromium получает антибот-страницу Яндекс SmartCaptcha («Вы не робот?») на всех страницах сайта. Headed Chromium и Firefox (в том числе headless) проходят без неё. Поэтому браузер по умолчанию — Firefox. Обход защиты (подмена user-agent и т. п.) не используется.
- **Создание заказа.** Заказ на боевом сайте не создаётся без разрешения владельца (предусловие ТК-КП-03-15). Шаги 1–5 выполняются полностью, а шаг 6 в отчёте помечается как **skipped** с причиной «заблокирован». По ТЗ такой сценарий **не считается пройденным**. Страница подтверждения заказа (`OrderSuccessPage`) не проверена на реальной разметке.
- **Без учётной записи** позитивные проверки, «неверный пароль» и сквозной сценарий пропускаются (skipped) с причиной в отчёте.
- **Неверный пароль.** Каждый прогон делает 2 неудачные попытки входа в тестовый аккаунт. Блокировки после них не замечено (проверено 6 попыток подряд на несуществующем email).
- **Не автоматизировано:** регистрация и восстановление доступа — там CAPTCHA и SMS (ТК-Р-07, ТК-А-10 и др.).
- **Пункт самовывоза.** Иногда сайт открывает окно выбора пункта на карте. Тест это обрабатывает и выбирает пункт из данных (`pickupPoint`).

## Логи и отчёт

- Логи пишутся в консоль и в `logs/autotest.log`. Лог каждого теста прикладывается к нему в Allure.
- В Allure есть: название с ID кейса, статус, метки (`case_id`, epic/feature/story, severity, теги связанных ТК), шаги, параметры набора, окружение.
- При падении прикладываются скриншот с закрашенными полями ввода (или причина, почему его нет) и место сбоя. Скриншот и лог лежат в теле теста (Test body), после шагов.
- **Защита данных:**
  - пароли передаются в Allure только как `***`;
  - логи маскируют email, телефоны, токены и cookies. В начале каждого теста в лог пишется строка «Маскирование включено…» со списком того, что скрывается (без самих значений). Каждый ввод в поле логируется с пометкой, например `Ввод в «Пароль»: *** [замаскировано: пароль]`;
  - после прогона `SanitizingReporter` вычищает зарегистрированные секреты из всех текстовых результатов, включая снимок страницы `error-context.md`;
  - trace и video выключены, потому что в них попали бы введённые данные.
